## 关于这个 Notebook

这是一个**通用评估 Harness（Evaluation Harness）**示例，技术栈为 LangGraph + OpenRouter。

Notebook 用“客服工单”作为案例，演示一个真实、非 mock 的 Agent 评估框架。它复现了交互式评估面板中最核心的机制：

1. 构造结构化测试场景；
2. 以受控并发方式异步生成结果；
3. 分批评分，组合 LLM Judge 与确定性检查；
4. 通过后台 worker 实时跟踪执行进度；
5. 按违规项排序，交给领域专家复核，并导出 CSV。

这里真正要学习的不是“客服工单”，而是**如何把 Agent 的质量评估做成一套可重复运行的工程流程**。

---

## 评估流水线的核心结构

整个流程可以理解为：

```text
场景输入
   ↓
阶段 1：并发生成（bounded semaphore）
   ├─→ 生成错误桶
   ↓
阶段 2：批量 LLM 评分
   ↓
确定性检查 + 违规标记
   ↓
按违规优先级排序
   ↓
导出 CSV，交给领域专家复核
```

它同时保留以下几类信息：

- 场景输入；
- 生成提示词；
- 模型原始输出；
- 解析后的结构化结果；
- Judge 提示词与 Judge 原始输出；
- 规则分、LLM 分、最终分；
- 违规项；
- 生成耗时与错误信息。

这比只保存一个“总分”更重要，因为真正的评估必须能够追溯：**为什么这个样本得低分？问题出在模型、提示词、工具调用、结构化输出还是评分器？**

## 如何编写有效的评估场景

高质量场景不只是描述“要做什么”，还需要定义 Agent 在什么上下文里行动，以及审核者应该观察什么。

### 1. 明确定义成功标准

- 写清预期行为、约束与可接受的解决方式；
- 给出审核者可以直接验证的成功信号。

不要只写“正确处理工单”，而应写成类似：

- JSON 输出必须合法；
- 解决步骤至少 3 条，并且有先后顺序；
- 不能丢失登录、SSO、错误码等关键信息。

### 2. 主动加入边界案例

- 加入信息不完整、压力大、涉及政策或安全边界的情况；
- 这些场景更容易暴露推理、工具调用与升级逻辑中的弱点。

只测“理想输入”，很容易得到虚假的高分。

### 3. 有意识地使用 Persona

- 覆盖不同知识水平、表达方式和期待的用户；
- 不要让所有测试样本都来自“表达清楚、懂技术、配合度高”的理想用户。

Persona 的价值在于检查模型是否真正适配不同用户，而不是只对一种沟通风格表现良好。

### 4. 把场景当作对话轨迹，而不是单轮 Prompt

- 评估应考虑多轮交互轨迹；
- 写清预期追问、澄清点、以及何时应该升级人工或进入其他流程。

例如，当关键信息缺失时，Agent 不应该直接猜答案，而应该先问一个澄清问题。

### 5. 显式定义压力维度（Stress Dimension）

Notebook 中用了 5 类压力维度：

- `urgency`：用户需要立即解决问题；
- `ambiguity`：关键信息缺失，Agent 应主动澄清；
- `emotional_frustration`：用户愤怒或不信任，回复需要降温；
- `knowledge_mismatch`：用户误解系统机制，回复需要解释；
- `adversarial_intent`：用户尝试绕过安全措施，Agent 必须守住策略边界。

一个实用的测试场景通常至少包含：Persona、情绪状态、压力维度、背景、用户目标和预期对话路径。

## 一个实用的场景模板

Notebook 中的 `SCENARIO_TEMPLATE` 可以抽象为：

```text
scenario_id        场景唯一标识
persona            用户角色与专业水平
emotional_state    情绪状态
background         已知背景和系统状态
user_goal          用户真正想达成的目标
expected_flow      预期的对话/处理路径
success_criteria   可验证的成功标准
```

这套结构的意义是把“测试样例”从一条 Prompt 升级为**一个带上下文和验收标准的测试合同**。

## 两类评分为什么要同时存在

Notebook 同时用了：

### 确定性检查（Deterministic Checks）

例如：

- 是否包含必要关键词；
- `resolution_steps` 是否少于 3 条；
- `summary` 是否过短；
- 是否违反对应的压力维度要求。

优势：

- 可解释；
- 稳定；
- 便宜；
- 非常适合 CI/CD 门禁。

局限：

- 很难评估“表达是否清楚”“方案是否真正可执行”这类软质量。

### LLM Judge

Judge 对输出的清晰度、正确性和可执行性进行 0–1 评分，并给出理由。

优势：

- 能处理语义质量；
- 比关键词规则更灵活。

局限：

- 本身也可能漂移；
- 成本更高；
- 需要保留 Judge 输入输出才能审计。

因此 Notebook 不是二选一，而是把二者组合起来。例如示例中的最终分数采用：

```text
final_score = 0.4 × det_score + 0.6 × llm_score
```

具体权重并不是通用答案；真正重要的是**硬规则与语义评分分层**。

## 为什么要限制并发并分批评分

生成阶段使用 `asyncio.Semaphore` 限制并发，评分阶段采用 batch。

这解决三个工程问题：

1. 防止短时间请求过多触发模型供应商限流；
2. 避免评估规模扩大后成本与延迟失控；
3. 让进度可以被稳定跟踪，而不是一次性黑盒运行。

Notebook 把生成阶段映射到 0–60% 进度，评分阶段映射到 60–95%，最后再做汇总。

这并不是算法要求，而是一个很实用的生产模式：**评估任务也需要可观测性。**

## 如何适配到自己的业务

这份模板可以直接迁移到其他领域：

- 把示例工具替换为你自己的领域工具；
- 把 `TicketScenario` / `TicketOutput` 替换成业务真实 Schema；
- 保留同样的评估机制：受控并发、批量评分、进度跟踪、违规优先审核；
- 增加真正重要的确定性检查，例如 Schema、合规规则、策略边界、风格约束；
- 将明细结果保存到 CSV / Parquet / 数据库；
- 在模型或 Prompt 上线前，在 CI/CD 中使用阈值门禁。

对研究类 Agent，也可以把 `TicketScenario` 替换为：

- 数据异常诊断任务；
- 文献检索任务；
- 预测实验设计任务；
- 回测分析任务；
- 结论复核任务。

## 领域专家复核流程（Domain-Expert Review Workflow）

Notebook 给出的实操闭环是：

1. 从真实用户字段或业务任务中抽取场景；
2. 执行异步评估，并实时展示阶段进度；
3. 优先查看规则违规、压力维度失败与低分样本；
4. 导出 CSV，让领域专家快速交叉检查。

关键要求是：**导出完整 Trace，而不是只导出聚合分数。**

完整 Trace 至少应该包括：

- 输入文本；
- 生成 Prompt；
- 生成原始输出；
- Judge Prompt；
- Judge 原始输出；
- 如果使用 RULER，则保留 RULER 日志；
- 所有确定性检查结果和错误信息。

这样，即使没有额外的 telemetry 平台，团队也能完成严肃的质量复核。

## 基于 Persona 的 RULER 评估

Notebook 后半部分增加了 Persona 条件下的场景，并使用 **RULER** 对候选输出进行相对评分。

这里有一个非常重要的使用原则：

> RULER 最适合对**同一个场景上下文中的多个候选轨迹**进行相对评分，而不是把完全不同的场景随意放在一起比较。

因此 Notebook 会针对同一个 Persona / 场景组生成多个候选结果，再对这些候选做相对排序。

### 为什么这样做有价值

- 可以检查输出是否真的适配不同用户背景和 Persona；
- 可以捕捉确定性规则难以发现的风格漂移、帮助度下降等问题；
- 可以继续复用同一套基于 OpenRouter 的评估栈。

Notebook 中也明确建议：一个 RULER group 最好包含多个候选，实践中 4–8 个候选更合适。候选太少时，相对排序的信息量很低。

---

## 这份 Notebook 最值得记住的 5 个原则

1. **评估对象不是单个答案，而是完整执行轨迹。** 需要保存输入、Prompt、模型输出、Judge、规则结果与错误信息。
2. **确定性规则与 LLM Judge 是互补关系。** 前者稳定可控，后者负责语义质量。
3. **场景设计决定评估上限。** 没有边界案例、Persona 与压力维度，再好的评分器也测不出真实弱点。
4. **先看失败与违规，再看平均分。** 真实生产风险通常藏在低频长尾，而不是平均值里。
5. **评估本身也要工程化。** 并发控制、进度、持久化、审计和 CI/CD 门禁都是评估系统的一部分。
