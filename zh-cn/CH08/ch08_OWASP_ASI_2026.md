# Chapter 8：OWASP ASI 2026 对抗性 Agent 评估

> 对应原 Notebook：`ch08/ch08_OWASP_ASI_2026.ipynb`
>
> 本文件用于中文阅读；代码、API、类名、函数名与原 Notebook 保持一致。

## 关于这份 Notebook

这份 Notebook 展示如何在**对抗性条件（adversarial conditions）**下构建并评估一个会调用工具的 Agent。

你会实现一个基于 **LangGraph** 的客户支持 Agent，并为它提供两个工具：

- `search_kb`：检索内部知识库；
- `send_email`：执行受限操作，必须获得用户的明确批准。

## 运行时硬约束

这个 Agent 不是只依赖 prompt 告诉模型“不要做坏事”，而是在运行时真正执行硬约束（hard constraints）：

- 限制工具调用预算；
- 对敏感操作做审批检查；
- 对违规调用进行明确阻断；
- 被阻断后给出原因说明。

这体现了一个关键原则：

> 安全规则应该尽量落实在 orchestration 和 tool boundary，而不是只存在于模型提示词里。

## 评估设置

接下来，Notebook 使用 **DeepTeam**，结合 OWASP 的 **ASI 2026 framework** 对 Agent 进行测试，重点关注：

- **ASI-02：Tool Misuse and Exploitation（工具误用与利用）**。

每次运行都会记录：

- 最终回复；
- 实际执行的工具；
- 被阻止执行的工具。

这意味着评估对象不再只是“最后一句回答是否看起来正确”，而是整个 Agent 在压力和诱导下的行为轨迹。

## 为什么这件事重要

这份 Notebook 强调的核心观点是：

> **Agent 的可靠性取决于编排（orchestration）和约束（constraints），而不只是模型本身的质量。**

如果一个模型很强，但可以绕过审批、无限调用工具、执行未经授权的动作，那么它仍然不能算可靠的生产系统。

因此，生产级 Agent 评估必须检查：

1. 它说了什么；
2. 它调用了什么工具；
3. 哪些动作被系统允许；
4. 哪些动作被系统阻断；
5. 在恶意诱导或边界条件下，这些约束是否仍然有效。

## 工具层面的安全设计

### `search_kb`

这是相对低风险的读取型能力。它代表 Agent 可以访问内部知识，但不直接产生外部副作用。

### `send_email`

这是典型的高风险、带副作用工具。发送邮件会对外部世界产生真实影响，因此不能仅由模型自己决定是否执行。

Notebook 将此类工具设计为受限 action，要求显式用户批准。这种模式可以迁移到：

- 发邮件；
- 发消息；
- 下单；
- 转账；
- 修改数据库；
- 删除文件；
- 创建或取消业务订单。

## Tool Budget 为什么也是安全机制

限制 tool budget 不只是为了控制 token 或 API 成本，也是在缩小 Agent 的行为边界。

如果一个 Agent 可以无限循环调用工具，那么即使每次单独调用看起来都合法，也可能通过长链条产生：

- 资源滥用；
- 重复副作用；
- 意外的数据暴露；
- DoS 式行为；
- 高成本失控。

因此 tool budget 本质上也是一种运行时治理策略。

## 为什么要记录“执行”和“阻断”两类工具

只记录成功执行的工具不够。

安全评估尤其需要知道：

- Agent **尝试**做什么；
- 系统 **允许**了什么；
- 系统 **阻止**了什么。

如果没有 blocked-tool 记录，你只能看到“最终没有执行危险动作”，却无法区分：

- Agent 根本没想这么做；
- Agent 想做，但安全层成功阻止了。

这两种情况在安全分析里完全不同。

## 对抗性评估和普通功能测试的区别

普通测试往往问：

> 正常用户输入时，Agent 能否完成任务？

对抗性评估则会进一步问：

> 当输入故意诱导 Agent 绕过规则时，系统还能否保持约束？

因此，它的重点不是验证“happy path”，而是系统性寻找边界失效点。

## 生产系统应该从这份 Notebook 学到什么

可以提炼成四条原则：

1. **高风险操作必须有程序化 gate**：不能只靠 prompt 约束；
2. **工具调用需要预算与权限边界**：防止无限执行和权限扩张；
3. **评估要覆盖行为轨迹**：不仅看 final answer，还要看 tool trace；
4. **安全测试必须包含 adversarial cases**：正常样本表现好，不代表上线后足够安全。

## 与普通 Evaluation Harness 的关系

Chapter 8 的两个 Notebook 可以看成互补：

- `ch08_eval_harness.ipynb` 更关注**质量评估体系**：场景、评分、judge、hard checks、专家复核；
- `ch08_OWASP_ASI_2026.ipynb` 更关注**安全与对抗性行为**：工具误用、审批边界、运行时阻断。

生产级 Agent 通常需要同时具备这两层评估：既要回答“做得好不好”，也要回答“会不会做出不该做的事”。
