# Chapter 2：ToT 风格多阶段写作 Agent

> 对应原 Notebook：`CH02/ch02_ToT.ipynb`

## 这份 Notebook 在解决什么问题

这份 Notebook 展示了一个小型、多角色的写作工作流：先生成多个候选方案，再由更严格的模型评审，接着调用搜索工具补充资料，最后基于选定方案和来源生成文章提纲与开头。

它体现的是一种 Tree-of-Thought（ToT，思维树）式思想：**不要让系统一次性押注一个答案，而是先生成多个候选分支，再比较、筛选、继续展开。**

这里不是完整实现通用 ToT 搜索算法，而是把 ToT 最有价值的工程思想落到一个可运行的 LangGraph 流程中。

## 四阶段工作流

整个图是线性的，但每一步职责明确：

1. **propose**：生成 3 个候选创意；
2. **reflect**：批判并选出最好的方案；
3. **research**：生成搜索查询，调用 SerpAPI，汇总来源；
4. **draft**：基于选中的方案和资料生成标题、受众描述、五段提纲和短引言。

虽然 Graph 本身是线性的，但“树”的部分发生在 `propose → reflect`：系统先展开多个分支，然后压缩回一个最优分支。

## 为什么要把角色分开

Notebook 没有让一个模型承担全部任务，而是区分：

- **创意生成器**：更偏发散；
- **评审模型**：更偏稳定和严格；
- **研究 Agent**：负责生成查询并调用搜索工具；
- **写作模型**：负责把结构化结果变成最终稿件。

这种设计的意义不是“多 Agent 看起来更高级”，而是让不同阶段可以采用不同提示、模型和温度参数。

例如：

- 创意阶段可以提高 temperature，鼓励差异化；
- Judge 阶段应接近确定性，降低随机选错的概率；
- 研究阶段更看重工具调用和结构化输出；
- 最终写作阶段只消费已经筛选、整理后的上下文。

## 结构化输出

Notebook 使用 Pydantic Schema 约束多个中间结果，例如：

- `OptionsPayload`：候选方案；
- `ChoicePayload`：最终选择及理由；
- 查询 Schema：研究阶段的搜索词。

通过 `with_structured_output(...)`，模型不再只返回自由文本，而是返回字段固定的数据结构。

这有两个直接好处：

1. 下游节点不需要重新解析自然语言；
2. Graph 的路由和状态更新更稳定。

在选择候选方案时，代码还会对返回的 index 做防御性 clamp，避免模型给出超出范围的索引。

## research 节点怎么工作

研究阶段不是直接让模型“写一段有来源的内容”，而是拆成三个动作：

1. 模型先生成 3–5 个精确查询；
2. 对每个查询调用 `internet_search` / SerpAPI；
3. 再把原始搜索结果压缩成结构化 `sources_json`，并给出建议引用。

这比让模型一次性完成“搜索 + 判断 + 写作”更可控，因为每一步都能单独观察和调试。

## LangGraph 在这里承担什么角色

Graph 中维护的是 Typed State，包含：

- 累积消息；
- 候选 options JSON；
- 选中 choice JSON；
- 研究得到的 sources；
- 最终 draft。

流程通过 `MemorySaver` 使用内存 Checkpoint，因此同一个 thread 可以在运行过程中保留状态。

Notebook 还会打印逐节点的 streaming trace，并渲染 Mermaid 图，让你可以观察：

`propose → reflect → research → draft`

## 这个模式为什么有效

### 1. 先发散，再收敛

单次生成最大的问题是：模型第一步走错，后面所有步骤都只能在错误方向上继续优化。

候选生成让系统保留多个可能性；Judge 则负责把计算资源集中到最值得继续的分支上。

### 2. 生成和评估分离

让同一个 prompt 一边创造、一边自我否定，往往会出现标准漂移。把生成器和评审器拆开，可以给它们不同目标函数。

### 3. 研究与写作分离

搜索结果先被压缩成结构化来源，再交给 Writer，可以降低写作阶段上下文噪声，并给后续增加事实核验器留下接口。

### 4. 每一阶段都有清晰产物

每个节点都生成明确的中间 artifact，因此你可以判断问题出在：

- 候选不够好；
- Judge 选错；
- 查询不够准；
- 搜索结果不足；
- Writer 没有利用好已有资料。

这比只看最终文章更容易优化。

## 这是不是严格意义上的 Tree-of-Thought

不完全是。

经典 ToT 通常包含更显式的：

- 多分支展开；
- 分支打分；
- 搜索策略（BFS / DFS / best-first 等）；
- 必要时回溯；
- 多轮扩展和剪枝。

这份 Notebook 更像是**一次展开 + 一次评审 + 继续执行**，属于 ToT 思想的轻量工程化版本。

因此不要把“四阶段 LangGraph”本身理解成 ToT。真正接近 ToT 的关键是：**候选空间 + 评估机制 + 选择机制**。

## 可以怎样扩展

- 在 `reflect` 后保留前 2 个方案，而不是只留 1 个；
- 对每个候选分别 research，再二次比较；
- 增加事实性检查和 Citation Verifier；
- 当 Judge 置信度不足时重新 propose；
- 将 Checkpoint 持久化到数据库；
- 最后增加 Markdown / HTML Formatter；
- 记录每个候选的 token 成本、质量分数和最终胜率，用于评估多分支是否值得。

## 对原 Notebook 的代码阅读提示

阅读时建议重点看四类接口：

1. `with_structured_output(...)` 如何把模型输出变成稳定 Schema；
2. `internet_search` 如何把外部搜索封装成工具；
3. Typed State 如何在节点之间传递 `options → choice → sources → draft`；
4. `MemorySaver` 和 streaming trace 如何让运行过程可恢复、可观察。

如果把这个案例迁移到研究任务，可以把四个节点替换成：

`提出研究假设 → 评审假设 → 搜集证据 → 形成结论`

因此它真正值得复用的不是“写博客”这个场景，而是**候选—评估—取证—产出**这一通用流程。
