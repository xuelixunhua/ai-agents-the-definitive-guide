# Chapter 6：Programmatic Tool Calling with Monty（程序化工具调用）

> 对应原 Notebook：`ch06/ch06_programmatic_tool_calling_monty.ipynb`

## 这份 Notebook 在解决什么问题

传统 Tool Calling 通常是：模型调用一次工具 → 把结果返回模型 → 模型再决定下一次调用。

当任务需要循环、排序、条件判断、聚合，或者一次性调用很多工具时，这种模式会产生大量模型往返、上下文膨胀和中间结果暴露。

这份 Notebook 展示 **Programmatic Tool Calling（程序化工具调用）**：让模型一次生成一段 Python 程序，由受限解释器在沙箱中执行，并在程序内部完成多次工具调用。

## 核心思路

传统模式：

```text
LLM → Tool A → LLM → Tool B → LLM → Tool C → LLM
```

程序化工具调用：

```text
LLM → 生成一段程序
          ↓
      Sandbox / Monty
      ├── Tool A
      ├── Tool B
      ├── 循环
      ├── 条件判断
      ├── 排序
      └── 聚合
          ↓
      最终结果
          ↓
         LLM
```

差别在于：**控制流从模型的多轮推理，转移到了代码执行环境。**

## 为什么这样更高效

### 1. 一次生成，多次调用

如果任务要查询 8 个城市，每个城市调用 2 个工具，传统模式可能需要模型参与 16 次甚至更多轮交互。

程序化工具调用可以让模型一次生成：

```python
for city in cities:
    pos = get_lat_lng(city)
    temp = get_temp(pos["lat"], pos["lng"])
    ...
```

之后 16 次工具调用都在沙箱内部完成。

### 2. 中间结果不进入模型上下文

大量坐标、温度、排序前结果等中间数据，不需要反复塞回模型上下文。

这样可以减少：

- token 消耗；
- 网络往返；
- 上下文污染；
- 模型被无关中间信息干扰的概率。

### 3. 代码天然表达控制流

循环、排序、过滤、切片、条件分支这类逻辑，Python 比单步 Tool Calling 更直接。

模型只需要规划一次，后续执行由代码完成。

## Monty 扮演什么角色

Notebook 使用 **Monty** 作为受限 Python 解释器。

关键点是：

- 模型生成代码；
- Monty 执行代码；
- 宿主机只暴露少量明确允许的函数；
- 文件系统、网络、导入、宿主全局变量默认不可访问。

因此，解释器本身构成一个执行边界（execution boundary）。

## Host Tools 与 Governed Surface

Notebook 中定义了普通 Python 函数，例如：

- `get_lat_lng(city)`
- `get_temp(lat, lng)`

这些函数实际运行在宿主环境中，可能持有凭证或访问网络。

模型看不到函数内部实现，只能看到你提供的接口说明。

这组可暴露函数，就是 **Governed Surface（受治理能力面）**。

换句话说：

> 模型能做什么，不取决于它会写多少 Python，而取决于宿主环境到底向沙箱开放了哪些函数。

## System Prompt 的约束作用

Notebook 的系统提示会明确约束生成代码，例如：

- 只能调用列出的 host functions；
- 只能使用基础 Python 控制流；
- 禁止 import；
- 禁止文件、网络和 OS 访问；
- 输入通过预定义变量提供；
- 最后一行必须是裸表达式，作为最终返回值。

这些规则不是安全边界本身，但能减少模型生成无效或越界代码。

真正的安全边界仍然必须由解释器和宿主权限控制来保证。

## `start()` / `resume()`：把执行变成可审批流程

程序化调用的一个关键能力，是可以把程序中的每个外部工具调用视为治理检查点。

大致流程可以理解为：

```text
程序开始执行
   ↓
遇到工具调用
   ↓
暂停
   ↓
策略检查 / 人工审批
   ↓
允许 → resume()
拒绝 → 阻断
```

如果解释器支持 snapshot，程序在暂停时的状态也可以被保存，之后继续执行，而不是从头运行。

这非常适合 Human-in-the-Loop（人在回路）或高风险工具审批。

## 这和普通 Tool Calling 的区别

| 维度 | 普通 Tool Calling | Programmatic Tool Calling |
|---|---|---|
| 控制流 | LLM 多轮决定 | 一段程序统一控制 |
| 工具调用次数 | 每次通常都回到模型 | 可在程序内批量执行 |
| 中间结果 | 经常进入模型上下文 | 可留在沙箱中 |
| 循环/排序/聚合 | 需要多轮推理 | 代码天然支持 |
| 可审计性 | 看调用轨迹 | 看代码 + 调用轨迹 |
| 风险 | 工具越权 | 还要额外考虑代码执行风险 |

## 安全边界

Notebook 特别强调：Monty 仍然是实验性技术。

已经存在通过公开漏洞赏金发现 sandbox escape 的案例，因此不能把“嵌入式解释器”当作绝对安全边界。

如果运行不可信模型生成的代码，更稳妥的做法是使用 **Defense in Depth（纵深防御）**：

1. Prompt 约束；
2. 解释器语言能力限制；
3. 只暴露白名单工具；
4. 关键工具审批；
5. 再把解释器放进容器、VM 或远程沙箱中；
6. 对 CPU、内存、执行时间、网络和文件权限做资源限制。

## 最容易理解错的地方

### 1. “让模型写 Python”不等于“让模型访问 Python 环境的一切”

正确做法是只给它受限解释器和明确开放的函数。

### 2. System Prompt 不是安全机制

Prompt 可以告诉模型“不要 import”，但真正禁止 import 的必须是运行时环境。

### 3. 程序化工具调用并不一定总比普通 Tool Calling 好

它更适合：

- 批量调用；
- 有循环和条件逻辑；
- 中间数据很多；
- 需要降低模型往返次数。

如果只调用一两个工具，普通 Tool Calling 反而更简单。

### 4. 安全重点从“工具调用”扩展到了“代码执行”

传统 Tool Calling 主要治理“能调用什么工具”；程序化调用还必须治理“代码能怎么组织这些工具”。

## 适用场景

比较适合：

- 批量查询多个对象；
- 数据聚合和排序；
- 多步骤 API 编排；
- 需要在本地处理中间结果；
- 需要降低 LLM round-trip；
- 需要对每个敏感工具调用增加审批。

不太适合：

- 单次简单工具调用；
- 执行环境无法安全隔离；
- 任务依赖大量不可预测的人类语义判断；
- 高风险环境但缺少 sandbox、权限和审计能力。

## 一句话总结

Programmatic Tool Calling 的核心，是把“模型逐步决定每一次工具调用”变成“模型先写一个受限程序，由沙箱批量完成控制流和工具编排”，从而减少模型往返和上下文开销，但同时必须把代码执行隔离与工具权限治理做得更严格。
